# bc-040 scored run — results

**2026-08-17.** `openai-agents 0.21.1` (subject) vs `langgraph 1.2.11` (same-day control),
gpt-4o, temperature 0, `parallel_tool_calls: false`, both forced onto Chat Completions.
160 scored attempts, 20 per subject per task — the first BenchClaw run at full protocol
compliance on runs-per-cell. Manifest: `methodology/bc040-manifest-v0.5.0.json`.

## Headline

**Correctness is a tie. Both arms completed 80/80.** Wilson 95% interval `[0.954, 1.000]`
for each — a perfect sample supports "at least 95.4%", not "100%". Zero failures in either
arm, so the failure taxonomy has no data from this run.

**openai-agents is measurably slower and measurably heavier on input tokens.** Paired by
`(task_id, run_index)` so provider drift cancels:

| metric | subject median | control median | delta | bootstrap 95% | verdict |
|---|---|---|---|---|---|
| wall time | 2.450s | 2.127s | **+0.310s** | `[+0.194, +0.455]` | real, ~15% slower |
| input tokens | 756 | 703 | **+52.5** | `[+33, +72]` | real |
| output tokens | 60 | 60 | 0 | `[0, 0]` | identical |
| cost per run | $0.00260 | $0.00253 | +$0.0001 | `[+0.0001, +0.0002]` | real, ~4.6% |

Latency spread: subject p95 3.442s, control p95 3.540s. The subject's median is higher but
its tail is not — LangGraph's slowest runs are slower.

## The token finding is the interesting one

The input-token delta is **deterministic per task**, not noisy. Every bootstrap interval on
`tokens_in` is zero-width within a task:

| task | input-token delta | wall-time delta |
|---|---|---|
| `inventory-reorder` | +18 (exact, every run) | +0.318s `[+0.191, +0.587]` |
| `recover-stale-revision` | +33 (exact) | +0.257s `[+0.084, +0.583]` |
| `dependent-shipping-quote` | +72 (exact) | +0.390s `[+0.110, +0.590]` |
| `refund-policy-minimal-tools` | +78 (exact) | +0.327s `[-0.008, +0.852]` — crosses zero |

That is tool-schema serialisation overhead, not model variance: the two SDKs describe the
same tools to the same endpoint with a fixed difference in bytes, and the gap grows with the
number and complexity of tools in the task. It is reproducible, explainable and nobody else
publishes it.

Note the one exception honestly: on `refund-policy-minimal-tools` the wall-time interval
crosses zero, so that task alone shows **no measurable latency difference**. The pooled
result is still outside the interval.

## What this can and cannot say

- Holds for gpt-4o at these four tasks. Not a general claim about either framework.
- The subject is OpenAI's own SDK measured on an OpenAI model. The control and the published
  raw data are the answer to the fairness objection; the page should raise it first.
- Both arms were forced onto Chat Completions. The SDK ships defaulting to the Responses API,
  so as-shipped latency may differ. Disclosed.
- `openai-agents 0.21.1` was one day old at measurement time.
- LangGraph 1.2.11 was re-measured from scratch. These numbers do not lay over the published
  1.2.9 benchmark.

## Two findings from build, not from the scored run

1. **Tracing is on by default in openai-agents and uploads to OpenAI** —
   `api.openai.com/v1/traces/ingest`, authenticated with our own key, and
   `OPENAI_AGENTS_TRACE_INCLUDE_SENSITIVE_DATA` defaults to *true*, so prompts and tool
   payloads go with it. LangGraph uploads nothing by default. Left on, it would have added an
   unmeasured round trip per run. Disabled three ways here. Publishable in its own right.
2. **The two frameworks classify bad tool arguments differently.** openai-agents rejects them
   outright (`malformed_tool_call`); LangGraph coerces the types and fails later at scoring
   (`invalid_final_answer`). Found in fake-mode acceptance tests, not in the scored run.
